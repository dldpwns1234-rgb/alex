# 기술 설계 — 서리 변경 (Frostmarch)

---

## 1. 엔진: Godot 4 + GDScript

### 왜 Godot인가

이 장르는 **렌더링이 아니라 시뮬레이션과 UI가 90%** 다.

| 엔진 | 판단 |
|---|---|
| **Godot 4** ✅ | 2D가 1급 시민(Unity처럼 3D에 2D를 얹은 구조가 아님). `TileMapLayer`와 노드 기반 UI가 이 장르에 정확히 맞음. 무료·오픈소스, 라이선스 리스크 0. 에디터가 가벼워 반복이 빠름 |
| Unity | 자료는 많지만 2D 전략 게임에 과함. 런타임 요금 사태 이후 신뢰도 이슈 |
| Phaser / 웹 | 배포는 쉽지만 시뮬레이션 규모가 커지면 툴링이 발목을 잡음 |
| LÖVE / 자체 엔진 | 첫 프로젝트에서 엔진까지 만들면 게임이 안 나옴 |

### 왜 GDScript인가

파이썬 유사 문법으로 진입이 빠르고, Godot API와의 마찰이 없다.
**성능 병목이 실제로 측정된 뒤에** 그 부분만 C# 또는 GDExtension(C++/Rust)으로 분리한다. 미리 하지 않는다.

## 2. 최우선 원칙 — 시뮬레이션과 엔진의 분리

```
res://
  sim/     ← 순수 GDScript. Node를 상속하지 않는다. 게임 로직 전부.
  game/    ← Godot 노드. sim의 상태를 읽어서 그리기만 한다.
```

### 왜 이게 최우선인가 — 밸런싱

전략·경영 게임은 **개발의 절반이 숫자 조정**이다.

- **분리되어 있으면:** 헤드리스로 100년치를 수 초 만에 돌려보고 "3년차에 항상 굶어 죽는다"를 그래프로 확인할 수 있다.
- **붙어 있으면:** 매번 손으로 플레이해야 한다. 그 순간 밸런싱을 포기하게 된다.

부수 효과로 얻는 것: 단위 테스트 가능, 세이브/로드가 단순 직렬화, 리플레이/결정론 확보.

### 규칙

1. `sim/` 아래 클래스는 `Node`, `Sprite2D` 등 엔진 타입을 **import조차 하지 않는다**
2. `sim/`은 렌더링·입력·시간(`delta`)을 모른다. **틱 번호만 안다**
3. `game/`은 `sim/`을 읽고 그린다. **역방향 참조 금지**
4. 플레이어 입력은 `game/` → **커맨드 객체** → `sim/` 순으로 흐른다 (직접 상태 변경 금지)

## 3. 시간 모델 — 두 개의 시계

경영과 전투는 시간 스케일이 다르다. 억지로 통일하지 않는다.

### 3.1 경영 시계 — 이산 틱

**하루 = 1틱.** 실시간이 아니다.

- 생산·소비·건설·이동·성장이 모두 틱 단위로 계산된다
- 렌더링은 틱 사이를 **보간**해서 부드럽게 보여준다 (운반꾼이 미끄러지듯 걷는 것처럼)
- 게임 속도(1x/2x/4x)는 **초당 틱 수**를 바꾸는 것일 뿐, 로직은 동일

**이점:** 디버깅·세이브·재현·밸런싱이 전부 쉬워진다. 부동소수점 누적 오차 문제가 없다.

### 3.2 전투 시계 — 고정 timestep

**20Hz 고정 timestep**으로 별도 시뮬레이션.

- 프레임레이트와 무관하게 동일한 결과 (결정론)
- 전투 중에는 **경영 시계 정지** (MVP 기준 — 단순화를 위해)

> **열린 질문:** 전투 중 경영을 계속 돌릴지. Manor Lords는 계속 돌린다.
> MVP는 정지로 시작하고, 재미가 확인되면 병행 실행을 검토한다.

## 5. 데이터 주도 설계

건물·병종·장비·몬스터·레시피는 **전부 데이터 파일**로 둔다. 코드에 숫자를 박지 않는다.

**형식:** Godot `Resource` (`.tres`) 또는 JSON

| | Resource (.tres) | JSON |
|---|---|---|
| 장점 | 에디터에서 편집, 타입 안전 | 외부 도구·스프레드시트 연동 쉬움 |
| 단점 | 대량 편집 불편 | 타입 검증 직접 구현 |

**권장:** JSON으로 시작. 밸런싱을 스프레드시트에서 하고 export하는 흐름이 가장 빠르다.
숫자가 안정되면 `.tres`로 전환을 검토한다.

예시:
```json
{
  "id": "bakery",
  "name": "화덕",
  "cost": { "wood": 20, "stone": 10 },
  "build_days": 6,
  "workers": 1,
  "recipe": { "in": { "flour": 2 }, "out": { "bread": 3 }, "days": 1 }
}
```

### 데이터 파일은 한 개, 읽는 계층은 두 개 (M1에서 정한 규칙)

위 예시에는 `name`("화덕")과 `cost`(숫자)가 한 파일에 같이 있다.
그런데 §2 규칙 2에 따르면 **sim은 한글 이름을 알아서는 안 된다.**

해법은 파일을 나누는 것이 아니라 **읽는 쪽을 나누는 것**이다:

| 계층 | 클래스 | 읽는 키 |
|---|---|---|
| sim | `SimBuildingCatalog` | `cost` · `build_days` · `workers` · `requires` |
| game | `BuildingDisplay` | `name` · `description` |

밸런싱을 스프레드시트 한 장으로 하면서도(§5의 목적) sim은 문구를 모르는 상태로 남는다.
헤드리스 밸런싱(§8)에서 건물 이름은 한 번도 필요하지 않다.

**대가:** 같은 파일을 두 번 파싱하므로 id가 어긋날 수 있다.
그래서 `tests/run_tests.gd`에 정합성 테스트를 둔다 — "모든 건물에 한글 이름이 있다",
"비용에 쓰인 자원이 전부 한글 이름을 갖는다", "선행 건물 id가 실제로 존재한다".
`data/village_layout.json`도 같은 방식이다 (sim은 `unlock_year`, game은 `x`/`y`).

## 6. 화면 구조와 상태 관리

> **물류 시뮬레이션은 폐기되었다** (GDD D13). 타일맵이 없으면 운반 동선이 존재하지 않는다.
> flow field · 운반꾼 유닛 · 경로 탐색이 전부 삭제되어 **기술 난이도가 크게 낮아졌다.**
> 그 대가로 부담이 UI 계층으로 이동했다. 이 절이 그 새 부담을 다룬다.

### 6.1 화면 스택

```
HomeScreen  (마을 전경)
    │ 건물 탭 → push
    ▼
BuildingScreen (건물별 서브클래스)
    │ 뒤로 → pop
    ▼
HomeScreen

BattleScreen  ← 습격/원정 발생 시 어느 화면에서든 진입 (모달)
```

**규칙**
1. 화면은 스택으로 관리한다. 안드로이드 **뒤로 가기 버튼 = pop**. 반드시 처리한다
2. 화면은 `sim` 상태를 **읽기만** 한다. 변경은 커맨드 객체를 통한다 (§2 규칙 4)
3. **어느 화면에 있든 게임 시계는 동일하게 흐른다.** 건물 화면에 들어가 있다고 시간이 멈추지 않는다

### 6.2 건물 화면의 공통 골격

건물 화면은 10종 이상 만들어야 한다(GDD §4.5). **중복 작업을 막는 것이 이 절의 목적이다.**

```
BuildingScreen (베이스 클래스)
├── 헤더        — 건물 이름 · 레벨 · 가동 상태
├── 인력 배정   — 슬라이더 (모든 건물 공통, GDD §4.6)
├── 자원 표시   — 투입/산출 현황
├── [고유 영역] ← 서브클래스가 채우는 유일한 부분
└── 푸터        — 업그레이드 · 철거
```

**고유 영역만 건물마다 새로 만든다.** 나머지는 베이스가 제공한다.
새 건물 추가 비용을 "화면 하나"에서 "패널 하나"로 낮추는 것이 목표다.

### 6.3 홈 화면

- 마을 전경은 **세로 스크롤 파노라마**. 타일맵이 아니라 배치된 스프라이트 집합
  - 슬롯은 좌우로 엇갈리게 놓아 굽이진 마을길처럼 보이게 한다
  - 가로 스크롤은 두지 않는다 — 세로 화면에서 가로로도 밀어야 하면 슬롯 절반이 늘 화면 밖이다

> **슬롯은 Button이 아니다 — 드래그 스크롤 때문이다.**
>
> Button은 터치를 소비한다. 슬롯이 화면의 대부분을 덮고 있으므로,
> 슬롯 위에서 손가락을 끌면 그 이벤트가 ScrollContainer까지 오지 않아
> **사실상 스크롤이 불가능해진다.** 실기에서 확인된 문제다.
>
> 그래서 슬롯은 입력을 받지 않는 Panel(`mouse_filter = IGNORE`)로 두고,
> 탭 판정을 파노라마가 직접 한다: 누른 지점에서 24px 넘게 끌렸으면 스크롤,
> 제자리에서 뗐으면 탭.
>
> **같은 규칙이 스크롤 안에 들어가는 모든 것에 적용된다.**
> 건물 화면의 패널도 `IGNORE`다. 패널 안의 버튼은 그대로 눌린다 —
> `mouse_filter`는 그 컨트롤에만 적용되고 자식에게 상속되지 않는다.
>
> **주의:** `_gui_input()`을 재정의하면 안 된다. ScrollContainer의 스크롤 처리는
> C++에 있고, GDScript에서는 `super._gui_input()`으로 되돌릴 수 없다
> ("Cannot call the parent class' virtual function"). `gui_input` **시그널**에 붙는다.
- 건물 슬롯은 화면상 고정 좌표를 갖는다 (`data/village_layout.json`)
- 건물 상태에 따라 스프라이트 교체: 미건설 / 건설중 / 가동 / 정지 / 파손
- 경고 배지를 건물 위에 표시 (인력 없음 · 재료 없음 · 파손)
- 계절별 색조는 **셰이더 오버레이 1장**으로 처리한다. 계절마다 스프라이트를 새로 그리지 않는다

> **아트 절약 원칙:** 계절 변화·파손 표현은 가능한 한 셰이더와 오버레이로 처리한다.
> 건물 10종 × 상태 5종 × 계절 4종을 전부 그리면 200장이다. 현실적으로 불가능하다.

## 7. 전투 시뮬레이션

**하나의 엔진을 3용도로 재사용한다** (GDD D9): 거점 방어전 / 토벌 원정 / 교역로 호위.

```
BattleSim
├── 입력: 아군 3열 편성, 적 웨이브 구성, 후방 지원(성문/망루 레벨), 승패 조건
├── 20Hz 고정 timestep으로 진행
├── 유닛 AI: 상태 머신 (대기 → 교전 → 열 붕괴 시 후퇴/승격)
├── 플레이어 개입: 명령 포인트 소비형 커맨드
└── 출력: 승패, 생존자 목록, 획득 전리품, 마을 피해량
```

**배경·후방 지원·승패 조건만 갈아끼우면 세 모드가 모두 된다.** 이것이 이 설계의 핵심 이득이다.

**3열 구조의 기술적 이득 (GDD D15):** 길찾기·자유 이동·충돌 판정이 전부 불필요하다.
유닛은 자기 열에 속하고, 교전은 열 대 열로 해석된다.
`flow_field`, A*, 물리 엔진이 모두 코드베이스에서 빠진다 — **모바일 성능과 배터리에 결정적이다.**

**결정론 요구:** 동일 시드 + 동일 입력 → 동일 결과. 리플레이와 밸런싱 자동화의 전제 조건이다.
→ `randf()` 직접 호출 금지. 시드가 고정된 `RandomNumberGenerator` 인스턴스를 `sim`이 소유한다.

## 8. 헤드리스 밸런싱 하네스

> **초기 형태가 M2에 이미 들어와 있다** — `tests/balance_probe.gd`.
> 100일치를 자동으로 플레이하고 인구·식량·장작·고난을 찍는다.
>
> 이것이 단위 테스트와 다른 질문을 한다는 것을 M2에서 확인했다.
> 단위 테스트 192개가 전부 통과하는 상태에서 두 가지가 숨어 있었다:
> 만성 식량 부족이 아무 결과도 낳지 않는 것, 그리고 농부가 정확히
> break-even이라 마을이 영원히 성장할 수 없는 것.
> **"규칙이 맞게 도는가"와 "그 규칙으로 만든 게임이 살 만한가"는 다른 질문이다.**
>
> M6에서 여러 전략 × 여러 파라미터를 쓸어보는 형태로 확장한다.

**§2의 분리가 존재하는 이유.** 초기부터 만들어 둔다.

```bash
godot --headless --script tools/headless_balance.gd -- --years 100 --seed 42 --out balance.csv
```

출력: 연차별 인구 · 식량 잔고 · 장작 잔고 · 은화 · 병력 · 사망자 · 습격 결과

**활용:**
- "3년차에 항상 굶어 죽는다" 같은 구조적 결함을 몇 초 만에 발견
- 시드를 100개 돌려 **분산**을 확인 (운에 좌우되는 정도)
- 밸런스 수정 후 회귀 확인

---

## 9. 세이브 / 로드

`sim/` 상태 전체를 직렬화한다. `game/`은 저장하지 않는다 (sim에서 재구성 가능).

- 형식: JSON (개발 중 디버깅 용이) → 안정화 후 바이너리 전환 검토
- 버전 필드 필수. 세이브 호환성 깨질 때 마이그레이션 지점
- **전투 중 세이브는 MVP에서 제외**

---

## 10. 테스트

**GUT** (Godot Unit Test) 사용.

우선순위:
1. 생산 체인 계산 — 입력/출력 수량이 맞는가
2. 계절 전환 시 소비량 — 겨울 배율이 제대로 걸리는가
3. 전투 결정론 — 동일 시드가 동일 결과를 내는가
4. 세이브/로드 왕복 — 저장 후 로드한 상태가 원본과 동일한가

`sim/`이 순수하기 때문에 위 전부가 엔진 없이 테스트된다.

## 12. 플랫폼과 배포

### 12.1 개발 중 플레이테스트 — 웹 빌드 (M0에 포함)

**푸시할 때마다 폰/태블릿 브라우저에서 최신 빌드를 열어볼 수 있게 한다.**

```
git push → GitHub Actions → Godot 웹 익스포트 → GitHub Pages
                                                     ↓
                                       모바일 브라우저에서 URL 접속
```

**Godot 4.3부터 단일 스레드 웹 익스포트가 기본**이라 `Cross-Origin-Opener-Policy` /
`Cross-Origin-Embedder-Policy` 헤더가 필요 없다. 커스텀 헤더를 설정할 수 없는
GitHub Pages·itch.io에서도 그대로 동작한다. (4.3 이전에는 이것 때문에 흰 화면만 나왔다.)

**제약:**

| 항목 | 내용 |
|---|---|
| iOS Safari | WebGL 2.0 관련 문제가 남아 있음. 공식 권장은 Chromium 계열/Firefox. **보조 수단으로만 취급** |
| 성능 | 네이티브가 아닌 WebAssembly. M2의 운반꾼 200기 시뮬레이션은 폰 브라우저에서 버거울 수 있음 |
| 렌더러 | Compatibility 렌더러만 지원 (Forward+/Mobile 불가). 2D 게임이므로 문제 없음 |
| C# | **웹 익스포트 불가.** GDScript 선택(§1)이 이 선택지를 열어둔 셈 |

**성능이 부족해지면:** 동일 CI에서 **Android APK**를 빌드한다. 네이티브라 성능 차이가 크고
Godot의 Android 익스포트는 안정적이다. iOS는 Mac + Xcode + 개발자 계정이 필요해 사정이 다르다.

### 12.2 정식 출시 플랫폼 — 안드로이드 폰 (확정, GDD D12)

**모바일 전용으로 설계한다. PC 이식은 고려하지 않는다.**
개발·테스트 기기는 안드로이드 폰이므로 §12.1의 iOS Safari 이슈는 실무상 문제가 되지 않는다.

**배포 경로**
- 개발 중: 웹 빌드 → GitHub Pages (§12.1)
- 실기 검증: **Android APK** — CI에서 빌드해 직접 설치. 성능·터치 반응이 실제 조건과 동일
- 출시: Google Play

**이미 확보된 이점 — 기존 결정들이 우연히 모바일에 유리했다**

| 결정 | 모바일 이점 |
|---|---|
| 실시간 자동 전투 (D2) | RTS가 모바일에서 실패하는 원인은 유닛 마이크로 컨트롤. 우리는 그게 없다 |
| 3열 고정 진형 (D15) | 길찾기·물리 없음 → 저사양 기기에서도 안정. 배터리 유리 |
| 하루 = 1틱 이산 시뮬 (§3.1) | 백그라운드 복귀 시 상태 복원이 깔끔 |
| 2D · Compatibility 렌더러 | 구형 안드로이드 기기 대응 |
| 슬롯 배치 + 2단 화면 (D13/D14) | 좁은 화면에 정보를 계층으로 분산 |

**UI 규칙 (전 화면 공통)**
