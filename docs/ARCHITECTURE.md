# 기술 설계 — 서리 변경 (Frostmarch)

---

## 1. 엔진: Godot 4 + GDScript

### 왜 Godot인가

이 장르는 **렌더링이 아니라 시뮬레이션과 UI가 90%** 다.

| 엔진 | 판단 |
|---|---|
| **Godot 4** ✅ | 2D가 1급 시민(Unity처럼 3D에 2D를 얹은 구조가 아님). `TileMapLayer`와 노드 기반 UI가 이 장르에 정확히 맞음. 무료·오픈소스, 라이선스 리스크 0. 에디터가 가벼워 반복이 빠름 |
| Unity | 자료는 많지만 2D 전략 게임에 과함. 런타임 요금 사태 이후 신뢰도 이슈 |
| Phaser / 웹 | 배포는 쉽지만 시뮬레이션 규모가 커지면 툴링이 발목을 잡음 |
| LÖVE / 자체 엔진 | 첫 프로젝트에서 엔진까지 만들면 게임이 안 나옴 |

### 왜 GDScript인가

파이썬 유사 문법으로 진입이 빠르고, Godot API와의 마찰이 없다.
**성능 병목이 실제로 측정된 뒤에** 그 부분만 C# 또는 GDExtension(C++/Rust)으로 분리한다. 미리 하지 않는다.

## 2. 최우선 원칙 — 시뮬레이션과 엔진의 분리

```
res://
  sim/     ← 순수 GDScript. Node를 상속하지 않는다. 게임 로직 전부.
  game/    ← Godot 노드. sim의 상태를 읽어서 그리기만 한다.
```

### 왜 이게 최우선인가 — 밸런싱

전략·경영 게임은 **개발의 절반이 숫자 조정**이다.

- **분리되어 있으면:** 헤드리스로 100년치를 수 초 만에 돌려보고 "3년차에 항상 굶어 죽는다"를 그래프로 확인할 수 있다.
- **붙어 있으면:** 매번 손으로 플레이해야 한다. 그 순간 밸런싱을 포기하게 된다.

부수 효과로 얻는 것: 단위 테스트 가능, 세이브/로드가 단순 직렬화, 리플레이/결정론 확보.

### 규칙

1. `sim/` 아래 클래스는 `Node`, `Sprite2D` 등 엔진 타입을 **import조차 하지 않는다**
2. `sim/`은 렌더링·입력·시간(`delta`)을 모른다. **틱 번호만 안다**
3. `game/`은 `sim/`을 읽고 그린다. **역방향 참조 금지**
4. 플레이어 입력은 `game/` → **커맨드 객체** → `sim/` 순으로 흐른다 (직접 상태 변경 금지)

## 3. 시간 모델 — 두 개의 시계

경영과 전투는 시간 스케일이 다르다. 억지로 통일하지 않는다.

### 3.1 경영 시계 — 이산 틱

**하루 = 1틱.** 실시간이 아니다.

- 생산·소비·건설·이동·성장이 모두 틱 단위로 계산된다
- 렌더링은 틱 사이를 **보간**해서 부드럽게 보여준다 (운반꾼이 미끄러지듯 걷는 것처럼)
- 게임 속도(1x/2x/4x)는 **초당 틱 수**를 바꾸는 것일 뿐, 로직은 동일

**이점:** 디버깅·세이브·재현·밸런싱이 전부 쉬워진다. 부동소수점 누적 오차 문제가 없다.

### 3.2 전투 시계 — 고정 timestep

**20Hz 고정 timestep**으로 별도 시뮬레이션.

- 프레임레이트와 무관하게 동일한 결과 (결정론)
- 전투 중에는 **경영 시계 정지** (MVP 기준 — 단순화를 위해)

> **열린 질문:** 전투 중 경영을 계속 돌릴지. Manor Lords는 계속 돌린다.
> MVP는 정지로 시작하고, 재미가 확인되면 병행 실행을 검토한다.

## 5. 데이터 주도 설계

건물·병종·장비·몬스터·레시피는 **전부 데이터 파일**로 둔다. 코드에 숫자를 박지 않는다.

**형식:** Godot `Resource` (`.tres`) 또는 JSON

| | Resource (.tres) | JSON |
|---|---|---|
| 장점 | 에디터에서 편집, 타입 안전 | 외부 도구·스프레드시트 연동 쉬움 |
| 단점 | 대량 편집 불편 | 타입 검증 직접 구현 |

**권장:** JSON으로 시작. 밸런싱을 스프레드시트에서 하고 export하는 흐름이 가장 빠르다.
숫자가 안정되면 `.tres`로 전환을 검토한다.

예시:
```json
{
  "id": "bakery",
  "name": "화덕",
  "cost": { "wood": 20, "stone": 10 },
  "build_days": 6,
  "workers": 1,
  "recipe": { "in": { "flour": 2 }, "out": { "bread": 3 }, "days": 1 }
}
```

## 6. 물류 시뮬레이션

**결정: 운반을 추상화하지 않고 실제 유닛으로 시뮬레이션한다.** (GDD D6)

### 성능 전략

| 항목 | 방식 |
|---|---|
| 경로 탐색 | **Flow Field** — 목적지별로 방향 벡터 필드를 1회 계산해 모든 유닛이 공유. 유닛마다 A*를 돌리지 않는다 |
| 갱신 빈도 | 유닛 로직은 **초당 10회**. 렌더링만 60fps로 보간 |
| 규모 목표 | 동시 유닛 200기 이하에서 안정 동작 |

200기 이하라면 GDScript로 충분하다. 초과 시점에 최적화를 고민한다. **미리 하지 않는다.**

### 흐름

```
생산 건물 → (완성품 발생) → 운반 요청 큐 등록
              ↓
        유휴 운반꾼 배정 → flow field 따라 이동 → 창고 적재
              ↓
소비 지점(가구/대장간/교역소)이 요청 → 창고에서 반출 → 배달
```

**병목이 눈에 보이는 것이 설계 목표다.** 운반꾼이 부족하면 완성품이 생산 건물 앞에 쌓이는 것이 시각적으로 드러나야 한다.

## 7. 전투 시뮬레이션

**하나의 엔진을 3용도로 재사용한다** (GDD D9): 거점 방어전 / 토벌 원정 / 교역로 호위.

```
BattleSim
├── 입력: 지형 맵, 아군 유닛 목록, 적 유닛 목록, 승패 조건
├── 20Hz 고정 timestep으로 진행
├── 유닛 AI: 상태 머신 (탐색 → 접근 → 교전 → 후퇴)
├── 플레이어 개입: 명령 포인트 소비형 커맨드
└── 출력: 승패, 생존자 목록, 획득 전리품, 파괴된 건물
```

**맵과 승패 조건만 갈아끼우면 세 모드가 모두 된다.** 이것이 이 설계의 핵심 이득이다.

**결정론 요구:** 동일 시드 + 동일 입력 → 동일 결과. 리플레이와 밸런싱 자동화의 전제 조건이다.
→ `randf()` 직접 호출 금지. 시드가 고정된 `RandomNumberGenerator` 인스턴스를 `sim`이 소유한다.

## 9. 세이브 / 로드

`sim/` 상태 전체를 직렬화한다. `game/`은 저장하지 않는다 (sim에서 재구성 가능).

- 형식: JSON (개발 중 디버깅 용이) → 안정화 후 바이너리 전환 검토
- 버전 필드 필수. 세이브 호환성 깨질 때 마이그레이션 지점
- **전투 중 세이브는 MVP에서 제외**

---

## 10. 테스트

**GUT** (Godot Unit Test) 사용.

우선순위:
1. 생산 체인 계산 — 입력/출력 수량이 맞는가
2. 계절 전환 시 소비량 — 겨울 배율이 제대로 걸리는가
3. 전투 결정론 — 동일 시드가 동일 결과를 내는가
4. 세이브/로드 왕복 — 저장 후 로드한 상태가 원본과 동일한가

`sim/`이 순수하기 때문에 위 전부가 엔진 없이 테스트된다.

## 12. 플랫폼과 배포

### 12.1 개발 중 플레이테스트 — 웹 빌드 (M0에 포함)

**푸시할 때마다 폰/태블릿 브라우저에서 최신 빌드를 열어볼 수 있게 한다.**

```
git push → GitHub Actions → Godot 웹 익스포트 → GitHub Pages
                                                     ↓
                                       모바일 브라우저에서 URL 접속
```

**Godot 4.3부터 단일 스레드 웹 익스포트가 기본**이라 `Cross-Origin-Opener-Policy` /
`Cross-Origin-Embedder-Policy` 헤더가 필요 없다. 커스텀 헤더를 설정할 수 없는
GitHub Pages·itch.io에서도 그대로 동작한다. (4.3 이전에는 이것 때문에 흰 화면만 나왔다.)

**제약:**

| 항목 | 내용 |
|---|---|
| iOS Safari | WebGL 2.0 관련 문제가 남아 있음. 공식 권장은 Chromium 계열/Firefox. **보조 수단으로만 취급** |
| 성능 | 네이티브가 아닌 WebAssembly. M2의 운반꾼 200기 시뮬레이션은 폰 브라우저에서 버거울 수 있음 |
| 렌더러 | Compatibility 렌더러만 지원 (Forward+/Mobile 불가). 2D 게임이므로 문제 없음 |
| C# | **웹 익스포트 불가.** GDScript 선택(§1)이 이 선택지를 열어둔 셈 |

**성능이 부족해지면:** 동일 CI에서 **Android APK**를 빌드한다. 네이티브라 성능 차이가 크고
Godot의 Android 익스포트는 안정적이다. iOS는 Mac + Xcode + 개발자 계정이 필요해 사정이 다르다.

### 12.2 정식 출시 플랫폼 — 미결정

> **열린 질문. 나중으로 미룰 수 없는 결정이다.**
> 모바일을 정식 타겟으로 삼으면 UI 전면 재작업을 의미하므로, 늦어도 M5(아트 투입) 전에는 확정한다.

**모바일에 유리한 기존 결정들 (이미 확보된 것):**

| 결정 | 모바일 이점 |
|---|---|
| 실시간 자동 전투 (GDD D2) | RTS가 모바일에서 실패하는 원인은 유닛 마이크로 컨트롤. 우리는 그게 없다. 명령 포인트 3~5개 = 큰 버튼 몇 개 |
| 하루 = 1틱 이산 시뮬 (§3.1) | 배터리에 관대. 백그라운드 복귀 시 상태 복원이 깔끔 |
| 2D · Compatibility 렌더러 | 저사양 기기에서도 동작 |

**모바일에 불리한 것:**

- 도시 빌더는 **정보 밀도**가 생명인데 폰 화면이 좁다
- **마우스 호버 툴팁이 없다** — 이 장르는 정보 전달의 상당 부분을 호버에 의존한다
- 우클릭 없음, 손가락이 화면을 가림, 오조작 위험

**권장: 태블릿 우선.**
폰까지 지원하려면 그리드 타일 확대, 건물 종류 축소, 정보 패널 단계 분할이 필요하다.
**게임 자체를 단순화해야 한다는 뜻이다.** 태블릿은 그런 희생 없이 가능하다.

**폰을 정식 타겟으로 확정할 경우 필요한 변경:**

- 최소 터치 타겟 44px 이상 → 타일 크기와 UI 밀도 재설계
- 롱프레스 = 우클릭, 핀치 = 줌
- 건설 시 **확정 버튼** (탭 즉시 배치는 오조작을 유발)
- 호버 툴팁 → 탭 시 하단 정보 바
- 동시 유닛 수 상한 하향 (200 → 100 이하)
